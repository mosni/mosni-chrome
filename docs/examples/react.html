@mosni/react is a third first-class authoring path for mosnicat, alongside the <mosni-*> custom elements and the plain HTML/class form. Every component renders the same DOM natively in React — no custom element is involved, so there is no child-ownership conflict, no upgrade timing, and server rendering is correct on first paint.

Install

Not published to a registry — depend on the tarball URL directly (npm records the resolved URL and an integrity hash in the lockfile, so this stays reproducible and pinned): 

"@mosni/react": "https://ui.mosni.dev/mosni-react-0.1.0.tgz"

react >= 18 is a peer dependency — bring your own.

Keep the bootstrap script tag

The React package ships zero CSS. Keep the usual mosnicat bootstrap for styling/fonts/favicon/viewport — a theme or colour change still lands on every app with no redeploy: 

<script src="https://mosni.dev/mosnicat.js"></script>

Conventions

  • Named exports, PascalCase: import { Panel, Field } from "@mosni/react".
  • Props are camelCase counterparts of the documented kebab attributes: no-logo → noLogo, filter-threshold → filterThreshold.
  • Booleans are real booleans, never presence-strings.
  • A slot with a plain-text attribute twin takes a ReactNode and covers both: <Header brand="MOSNI'S"> and <Header brand={<img />}> are both valid.
  • Events become on* callbacks: mosni-tab-change → onChange(index, label), mosni-dropdown-select → onSelect(value).
  • Every stateful component supports both controlled and uncontrolled use, React-idiomatically: selectedIndex/defaultSelectedIndex, open/defaultOpen, checked/defaultChecked, value/defaultValue.
  • ref forwards to the root DOM element; className is merged with the component's own classes, never replaced.

Types-only step (no runtime change)

Add JSX.IntrinsicElements declarations for every <mosni-*> tag with one import, and delete any hand-maintained declare module "react" { namespace JSX { … } } block doing the same job: 

import "@mosni/react/elements";

This alone type-checks existing <mosni-*> markup with zero behavioural change. Adopt individual <X> React components only where the ownership bugs actually bite.

SSR

Every component is SSR-safe: nothing reads window/document at module scope, and generated ids use useId() (never a module-level counter, which would desync between server and client). One thing to expect in the rendered HTML: React 19 hoists resource hints for anything containing an <img> (<Logo>, and by extension <Header>/<Layout>) — a <link rel="preload" as="image"> ahead of the component's own markup. That's correct, useful output your document head absorbs on hydration, not a bug.

A few components — <Modal>, <Tooltip>, <Lightbox>'s open overlay — portal their floating content to document.body. A portal cannot render during SSR (there is no document.body yet), so these render only their non-portalled part (e.g. a modal's trigger button) until the client mounts and the portal takes over.

The version-locking caveat

A React consumer's component markup updates only when the app bumps the @mosni/react package version; CSS still updates live from the CDN bootstrap. This is not a regression — the hand-written class path is first-class forever and has exactly the same property. Both authoring paths trade a little freshness for stability at a page's build time; only the custom-element path picks up markup changes without a redeploy.
